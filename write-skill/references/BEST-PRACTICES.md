## 基本原則

### 簡潔さが鍵

Claude はすでに賢い。Claude がまだ持っていないコンテキストのみを追加する。情報のひとつひとつを問い直す:
- 「この説明は Claude に本当に必要か？」
- 「Claude はこれを既知として扱えるか？」

**良い例（約 20 トークン）:**
```python
import pdfplumber
with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```

**悪い例（約 60 トークン）:**
> PDF（Portable Document Format）ファイルはテキスト・画像・その他のコンテンツを含む一般的なファイル形式です。PDF からテキストを抽出するにはライブラリを使う必要があります。利用可能なライブラリはたくさんあります…

良い例は、Claude が PDF とは何か、ライブラリの使い方を知っていることを前提としている。

### 自由度のレベル（詳細）

**高い自由度**（複数のアプローチが有効な場合）:
```md
## コードレビューのプロセス

1. コードの構造と整理を分析する
2. 潜在的なバグやエッジケースを確認する
3. 読みやすさと保守性の改善を提案する
```

**中程度の自由度**（望ましいパターンがある場合）:
```python
def generate_report(data, format="markdown", include_charts=True):
    # データを処理する
    # 指定されたフォーマットで出力を生成する
```

**低い自由度**（操作が脆弱な場合）:
```md
## データベースのマイグレーション

このスクリプトを正確に実行する:
```bash
python scripts/migrate.py --verify --backup
```
コマンドを変更したり追加フラグを付けたりしないこと。
```

## 段階的開示のパターン

SKILL.md は目次である。Claude は必要な場合のみ追加ファイルを読み込む（アクセスされるまでトークンコストはかからない）。

### パターン 1: 高レベルガイドとリファレンス

```md
## 高度な機能

**フォームへの入力**: 完全なガイドは [FORMS.md](FORMS.md) を参照
**API リファレンス**: すべてのメソッドは [REFERENCE.md](REFERENCE.md) を参照
```

### パターン 2: ドメイン別の構成

スキルが複数のドメインをカバーする場合、ドメイン別にコンテンツを整理して Claude が必要なものだけ読み込めるようにする:

```
bigquery-skill/
├── SKILL.md
└── references/
    ├── finance.md    # 収益・請求メトリクス
    ├── sales.md      # 案件・パイプライン
    └── product.md    # API 使用状況・機能
```

```md
## 利用可能なデータセット

**財務** → [references/finance.md](references/finance.md) を参照
**営業** → [references/sales.md](references/sales.md) を参照
```

### パターン 3: 条件付き詳細

```md
## ドキュメントの編集

簡単な編集は XML を直接変更する。

**変更履歴の追跡**: [REDLINING.md](REDLINING.md) を参照
**OOXML の詳細**: [OOXML.md](OOXML.md) を参照
```

### リファレンスのルール

- すべてのリファレンスは SKILL.md から**1 階層の深さ**に収める（`a.md → b.md → c.md` は NG。Claude が途中まで読んで詳細を見逃す可能性がある）
- 100 行を超えるリファレンスファイルには先頭に目次を追加する

## フィードバックループ

品質が重要なタスクには「検証 → 修正 → 繰り返し」のループを使用する:

```md
## ドキュメント編集プロセス

1. `word/document.xml` を編集する
2. **すぐに検証する**: `python scripts/validate.py unpacked_dir/`
3. 検証が失敗した場合:
   - エラーメッセージを注意深く確認する
   - 問題を修正する
   - 再度検証を実行する
4. **検証が通過した場合のみ次へ進む**
```

複雑な複数ステップのワークフローにはコピー＆ペースト可能なチェックリストを提供する:

```md
このチェックリストをコピーして進捗を管理する:

```
タスクの進捗:
- [ ] ステップ 1: フォームを分析する（analyze_form.py を実行）
- [ ] ステップ 2: フィールドマッピングを作成する（fields.json を編集）
- [ ] ステップ 3: マッピングを検証する（validate_fields.py を実行）
- [ ] ステップ 4: フォームに入力する（fill_form.py を実行）
```
```

### エッジケースを Claude に丸投げするスクリプト

```python
# 悪い例 — 失敗して Claude に解決を委ねるだけ
def process_file(path):
    return open(path).read()

# 良い例 — エラーを明示的に処理する
def process_file(path):
    try:
        with open(path) as f:
            return f.read()
    except FileNotFoundError:
        print(f"ファイル {path} が見つからないため、デフォルトを作成します")
        with open(path, "w") as f:
            f.write("")
        return ""
```

### マジックナンバー（意味不明な定数）

```python
# 悪い例
TIMEOUT = 47
RETRIES = 5

# 良い例 — 自己説明的
REQUEST_TIMEOUT = 30  # ほとんどの HTTP リクエストは 30 秒以内に完了する
MAX_RETRIES = 3       # 断続的な失敗のほとんどは 2 回目の再試行までに解決する

## テストと評価

### 使用するすべてのモデルでテストする

- **Haiku**（高速で低コスト）: スキルは十分なガイダンスを提供しているか？
- **Sonnet**（バランス型）: スキルは明確で効率的か？
- **Opus**（高い推論能力）: スキルは過剰な説明をしていないか？

Opus で機能するものが Haiku では詳細不足になる場合がある。

### 評価ドリブン開発

詳細なドキュメントを書く**前に**評価を構築する:

1. スキルなしで Claude に代表的なタスクを実行させ、具体的な失敗を記録する
2. それらのギャップを対象とした 3 つ以上の評価シナリオを作成する
3. ベースライン（スキルなしの Claude のパフォーマンス）を確立する
4. 評価を通過するための最小限の指示を書く
5. 繰り返す: 評価を実行 → ベースラインと比較 → 改善

**評価の構造:**
```json
{
  "skills": ["writing-skill"],
  "query": "PDF フォームを処理するスキルを作成して",
  "expected_behavior": [
    "有効なフロントマター（name, description）を持つ SKILL.md を作成する",
    "description は三人称で Use when トリガーを含む",
    "SKILL.md 本文が 500 行以内",
    "リファレンスは 1 階層の深さに収まっている"
  ]
}
```

### Claude A/B を使った反復改善

- **Claude A**: スキル指示の設計と改善を支援する
- **Claude B**: スキルを実際のタスクで使用する新しいインスタンス

Claude B の動作を観察 → 知見を Claude A に持ち帰る → 更新 → 繰り返す。
